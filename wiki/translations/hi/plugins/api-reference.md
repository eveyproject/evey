# प्लगइन API संदर्भ

यह दस्तावेज़ Evey प्लगइन लिखने वाले बाहरी डेवलपरों के लिए है। प्लगइन पर लागू सुरक्षा पाबंदियों के लिए [`security-model.md`](security-model.md) देखें।

## मैनिफ़ेस्ट स्कीमा

हर प्लगइन ZIP की जड़ में एक `plugin.yaml` होना चाहिए।

```yaml
name: my-plugin              # ज़रूरी; पढ़ने योग्य नाम
version: 1.2.3               # ज़रूरी; semver
kind: plugin                 # ज़रूरी; "plugin" होना चाहिए (केवल CSS/JS थीम के लिए "theme")
language: nodejs             # प्लगइन के लिए ज़रूरी; nodejs | python | go | php | ruby | lua | bash | sh
entrypoint: node index.js    # प्लगइन के लिए ज़रूरी; इंटरप्रेटर द्वारा चलाई जाने वाली पूरी कमांड लाइन:
                              # पहला शब्द इंटरप्रेटर है, PATH में खोजा जाता है;
                              # बाक़ी शब्द स्क्रिप्ट/आर्ग्युमेंट हैं, ZIP तक सीमित पाथ के साथ।
                              # "language" केवल यह जाँचने के लिए है कि रनटाइम उपलब्ध है और
                              # SDK स्टब कॉपी करने के लिए: यह entrypoint शुरू नहीं करता।

description: "..."           # वैकल्पिक
author: "..."                # वैकल्पिक
min_evey_version: "1.0.0"   # वैकल्पिक; semver में होस्ट का न्यूनतम संस्करण

permissions:
  - network                  # अनुमतियाँ सेक्शन देखें
  - media.read

external_fetch:              # "network" अनुमति घोषित होने पर ज़रूरी
  - api.themoviedb.org       # security-model.md में बाहरी पहुँच के नियम देखें
  - api.example.com          # केवल सादा होस्टनाम: कोई स्कीम नहीं, कोई वाइल्डकार्ड नहीं, कोई शाब्दिक IP नहीं

capabilities:
  - metadata.provider        # क्षमताएँ सेक्शन देखें

# वैकल्पिक: एक सब-डायरेक्टरी घोषित करें जिसकी सामग्री स्थैतिक संसाधनों के रूप में परोसी जाती है।
# फ़्रंटएंड मॉड्यूल घोषित होने पर ज़रूरी।
web_root: public/

# वैकल्पिक: होस्ट UI में डाले जाने वाले फ़्रंटएंड मॉड्यूल।
frontend:
  - slot: home.section       # security-model.md में स्लॉट सूची देखें
    src: public/front.js     # ZIP की जड़ से सापेक्ष पाथ; web_root के नीचे होना चाहिए

config_schema:               # वैकल्पिक; प्लगइन कॉन्फ़िग कुंजियों का वर्णन करने वाला JSON Schema ऑब्जेक्ट
  api_key:
    type: string
    secret: true             # या `type: password`: किसी क्लाइंट को कभी वापस नहीं भेजा जाता, एडमिन सहित
    description: "TMDB API key"
```

`secret: true` (या `type: password`) चिह्नित फ़ील्ड सामान्य रूप से सहेजा और प्लगइन को दिया जाता है, लेकिन हर पढ़ने वाला रूट, सार्वजनिक वाला और एडमिन कॉन्फ़िग पैनल, उसे छिपाकर लौटाता है। जब छिपा हुआ मान बिना बदले वापस भेजा जाए तो एडमिन पैनल सहेजा गया मान रखता है, इसलिए दूसरे फ़ील्ड सहेजने से कभी कोई रहस्य नहीं मिटता।

**इंस्टॉल पर लागू सत्यापन नियम:**

- `kind: plugin` को `language` और `entrypoint` चाहिए।
- `kind: theme` को `language`, `entrypoint` या `permissions` घोषित नहीं करने चाहिए।
- `frontend` ख़ाली न हो तो `web_root` ज़रूरी है।
- `frontend[].src` `web_root` के नीचे होना चाहिए।
- `frontend[].slot` सर्वर की ओर की स्लॉट श्वेतसूची में होना चाहिए।
- `network` अनुमति को एक ग़ैर-ख़ाली `external_fetch` सूची चाहिए।
- सभी `external_fetch` प्रविष्टियों को होस्ट-श्वेतसूची वैलिडेटर पास करना चाहिए।
- सभी क्षमताएँ और अनुमतियाँ सर्वर को ज्ञात होनी चाहिए।

## बैकएंड IPC

प्लगइन प्रोसेस और Evey होस्ट दो Unix डोमेन सॉकेट पर gRPC बोलते हैं, जिनके पाथ शुरू होते समय एनवायरनमेंट में दिए जाते हैं:

```
EVEY_PLUGIN_ID=<plugin_id>
EVEY_PLUGIN_SOCK=/tmp/evey/plugins/<plugin_id>/plugin.sock   # आपका प्रोसेस यहाँ सुनता है और PluginService देता है
EVEY_HOST_SOCK=/tmp/evey/plugins/<plugin_id>/host.sock       # HostService बुलाने के लिए आपका प्रोसेस यहाँ कनेक्ट करता है
```

होस्ट अपने सॉकेट पर प्लगइन प्रोसेस को उस PID से प्रमाणित करता है जो कर्नेल बताता है (`SO_PEERCRED`): प्रोसेस को ख़ुद कोई टोकन नहीं दिया जाता।

एक अलग, कम समय का JWT (5 मिनट, `plugin_id` + `user_id` तक सीमित) `IssuePluginToken` RPC से माँगने पर जारी होता है: प्लगइन का *फ़्रंटएंड iframe* अपने `public`/`prefs` दायरे वाले कॉल प्रमाणित करने के लिए एक लेता है। इसका ऊपर के बैकएंड सॉकेट से कोई संबंध नहीं और यह शुरू होते समय प्लगइन प्रोसेस को कभी नहीं दिया जाता।

gRPC सर्विस परिभाषाएँ `proto/plugin/v1/plugin_api.proto` में हैं। भाषा-विशेष SDK स्टब उसी proto से बनते हैं और प्लगइन ZIP में शामिल किए जा सकते हैं या साथ भेजे जा सकते हैं। कई भाषाओं के स्टब पहले से बने आते हैं (`sdk/<lang>/`); जो साथ नहीं आती उसे लक्ष्य बनाने के लिए देखें [dev-setup.md → किसी दूसरी भाषा के लिए स्टब बनाना](dev-setup.md#generating-stubs-for-another-language)।

होस्ट RPC स्तर पर अनुमतियाँ लागू करता है: ऐसा RPC बुलाना जिसे आपके मैनिफ़ेस्ट ने घोषित नहीं किया `PermissionDenied` देता है।

### डेटा स्टोर

हर प्लगइन को अपना स्थायी की/वैल्यू स्टोर मिलता है, प्लगइन के नेमस्पेस में: **कोई अनुमति नहीं चाहिए, प्लगइन अपने डेटा का मालिक है**। इसे कर्सर, कैश, आख़िरी सिंक के टाइमस्टैम्प, कुछ भी जो प्लगइन को रीस्टार्ट के बीच याद रखना है, उसके लिए इस्तेमाल करें। मान अपारदर्शी स्ट्रिंग हैं (संरचना चाहिए तो JSON ख़ुद एनकोड करें)।

| `HostService` RPC | उद्देश्य |
|---|---|
| `SetData(key, value)` | एक मान डालें या अपडेट करें। |
| `GetData(key) → {value, found}` | एक मान पढ़ें। |
| `DeleteData(key)` | एक कुंजी हटाएँ। |
| `ListDataKeys() → {keys}` | प्लगइन की कुंजियाँ सूचीबद्ध करें। |

प्लगइन id प्रमाणित सॉकेट से लिया जाता है: प्लगइन केवल **अपने ही** नेमस्पेस में पढ़/लिख सकता है, कभी किसी दूसरे प्लगइन के नहीं। प्लगइन अनइंस्टॉल होने पर उसका पूरा स्टोर अपने आप मिट जाता है (`ON DELETE CASCADE`), इसलिए हटाने के बाद कोई पुराना डेटा नहीं बचता।

यह स्टोर पूरे प्लगइन के लिए है। **हर उपयोगकर्ता** के लिए डेटा रखने के लिए (जैसे देख रहे उपयोगकर्ता की कोई पसंद), नीचे `prefs` अनुमति देखें: वह सतह प्लगइन के iframe से पहुँची जाती है, जहाँ उपयोगकर्ता संदर्भ मौजूद है।

## फ़्रंटएंड API

जब कोई प्लगइन `frontend` मॉड्यूल घोषित करता है, तो iframe `srcdoc` के HTML में एक ब्रिज स्क्रिप्ट होती है जो मॉड्यूल के JavaScript को `window.evey` देती है।

फ़्रंटएंड मॉड्यूल अपारदर्शी ओरिजिन वाले एक सैंडबॉक्स किए गए फ़्रेम में चलता है: उसकी होस्ट पेज के DOM, कुकी या स्टोरेज तक कोई पहुँच नहीं, और वह Evey तक केवल `window.evey` के ज़रिए पहुँचता है। उसकी अपनी नेटवर्क पहुँच फ़्रेम के `connect-src` से उसकी `external_fetch` सूची के होस्ट तक, `https://` पर, सीमित है; इस सूची के बिना प्लगइन कोई कनेक्शन नहीं खोल सकता।

### `evey.navigate(path)`

होस्ट एप्लिकेशन को `path` पर ले जाता है। पाथ `/home`, `/library`, `/media`, `/player`, `/settings` या `/search` से शुरू होना चाहिए; कुछ और (एडमिन क्षेत्र, साइन-इन, सेटअप, कोई पूर्ण या प्रोटोकॉल-सापेक्ष URL) चुपचाप छोड़ दिया जाता है।

```js
evey.navigate("/library/movies");
evey.navigate("/media/abc123");
```

### `evey.toast(level, message)`

होस्ट UI में एक टोस्ट सूचना दिखाता है।

- `level`: `"success"` | `"error"` | `"info"`
- `message`: सादा टेक्स्ट, अधिकतम 200 अक्षर, HTML हटाया जाता है
- प्रति सेकंड 3 टोस्ट तक सीमित

```js
evey.toast("success", "Metadata enriched.");
evey.toast("error", "API key missing.");
```

### `evey.resize(height)`

होस्ट से iframe स्लॉट को `height` पिक्सेल पर समायोजित करने को कहता है। 50-800 तक सीमित। `0` स्लॉट को समेट देता है: जिस प्लगइन के पास दिखाने को कुछ नहीं वह पेज पर जगह नहीं लेता।

```js
evey.resize(300);
evey.resize(0); // कहने को कुछ नहीं: स्लॉट ग़ायब हो जाता है
```

### `evey.onInit(callback)`

एक कॉलबैक दर्ज करता है जो तब एक बार चलता है जब होस्ट प्लगइन को उसका आरंभिक संदर्भ भेजता है। अगर `onInit` बुलाए जाने से पहले होस्ट `init` भेज चुका है, तो कॉलबैक तुरंत कैश किए गए डेटा के साथ बुलाया जाता है।

```js
evey.onInit(function(data) {
  // data.context         - प्लगइन कॉन्फ़िग मान (config_schema से)
  // data.locale          - सक्रिय भाषा स्ट्रिंग, जैसे "en-US"
  // data.theme           - सक्रिय थीम id
  // data.surface         - "web", "mobile" या "tv": विजेट कहाँ पहुँचा
  // data.suggestedHeight - केवल home.section: वहाँ होस्ट द्वारा सुझाई गई ऊँचाई (px)
  // data.viewportHeight  - केवल tv: पैनल की ऊँचाई dp में
});
```

होस्ट प्लगइन के `ready` संकेत के लिए 5 सेकंड तक इंतज़ार करता है (ब्रिज स्क्रिप्ट यह अपने आप करती है)। समय सीमा पार होने पर iframe हटा दिया जाता है और एक त्रुटि बताई जाती है।

#### ऊँचाई

`home.section` विजेट बिना कुछ किए `data.suggestedHeight` पर खुलता है: होस्ट जानता है कि उसने आपको किस सतह पर रखा है (डेस्कटॉप पेज, फ़ोन, टीवी पैनल) और वह ऊँचाई सुझाता है जो वहाँ मुखपृष्ठ विजेट की होती है, ताकि एक मुखपृष्ठ के सभी विजेट एक ही आकार के हों। `evey.resize()` केवल तब बुलाएँ जब आप बेहतर जानते हों; होस्ट आपकी जानकारी के बिना आपकी सामग्री का आकार कभी नहीं बदलता, न उसे स्केल करता है।

#### टीवी पर

टीवी ऐप आपके विजेट को एक WebView में चलाता है, और ब्राउज़र में सच कुछ बातें वहाँ सच नहीं रहतीं:

- **अपने ही viewport से आकार न लें।** WebView के अंदर `window.innerHeight` वही स्लॉट है जो होस्ट ने अभी आपको दिया: यह चक्रीय है। अगर आप अपना आकार बदलते हैं, तो `data.viewportHeight` (पैनल) या `data.suggestedHeight` से लें, कभी `innerHeight` से नहीं।
- **कोई फ़ोकस नहीं, कोई पॉइंटर नहीं।** विजेट को कभी D-pad फ़ोकस नहीं मिलता, और कोई hover नहीं होता। कुछ भी इंटरैक्टिव वेब और मोबाइल सतहों पर रखें।
- **टेक्स्ट को किनारों से दूर रखें।** टीवी ओवरस्कैन करते हैं: हर तरफ़ चौड़ाई और ऊँचाई का लगभग 5% ख़ाली छोड़ें।
- **WebGL को असली डिवाइस पर, ज़ूम करके परखें।** शेडर डिवाइस के GPU और उसके ड्राइवर पर चलता है, आपके डेस्कटॉप वाले पर नहीं। एक जाली हैश जो `fract()` से पहले अपने इनपुट को कुछ सौ से गुणा करता था, ब्राउज़र में ठीक दिखते हुए Mali GPU पर बादलों की जगह सपाट बहुभुज बनाता था; नॉइज़ निर्देशांक सीमित रखें (`mod()`) और सीमित मानों का हैश लें। `tests/plugins/weather-v2` ऊपर की सभी बातों के लिए संदर्भ विजेट है।

## स्लॉट

| स्लॉट | कहाँ दिखता है |
|---|---|
| `home.section` | मुखपृष्ठ पर सामग्री सेक्शन |
| `home.hero` | मुखपृष्ठ पर मुख्य बैनर क्षेत्र |
| `library.sidebar` | लाइब्रेरी दृश्यों में साइडबार पैनल |
| `media.detail.sidebar` | मीडिया विवरण पेजों पर साइडबार पैनल |
| `player.overlay` | वीडियो प्लेयर पर ओवरले परत |
| `settings.user.appearance` | उपयोगकर्ता सेटिंग्स में रूप-रंग उप-सेक्शन |
| `sidebar.bottom` | मुख्य नेविगेशन साइडबार का निचला क्षेत्र |
| `admin.nav` | एडमिन पैनल में एक नेविगेशन प्रविष्टि जो प्लगइन का अपना सैंडबॉक्स किया गया पेज खोलती है |

`admin.nav` एडमिन क्षेत्र का **एकमात्र** स्लॉट है। यह मौजूदा एडमिन स्क्रीन में UI नहीं डालता: यह एक मेनू प्रविष्टि जोड़ता है जो एक समर्पित एडमिन रूट पर एक सैंडबॉक्स किए गए iframe में आपके प्लगइन का अपना पेज खोलती है। इसे माँगना इंस्टॉल सहमति के अंतर में दिखता है।

`admin.*`, `login.*`, `setup.*`, `profile.security.*` के नीचे के बाक़ी सभी स्लॉट इंस्टॉल के समय मना होते हैं।

## क्षमताएँ

क्षमताएँ घोषित करती हैं कि प्लगइन सर्वर की ओर कौन-सी भूमिका निभाता है। ये प्रभावित करती हैं कि होस्ट प्लगइन को कौन-से RPC भेजता है और उसे अपनी सर्विस रजिस्ट्री में कैसे दर्ज करता है।

### `metadata.provider`

प्लगइन मीडिया आइटम के लिए समृद्ध मेटाडेटा दे सकता है। कोई समर्पित समृद्धि RPC नहीं है: होस्ट जिस `PluginService` को बुलाता है वह केवल `Initialize` / `Shutdown` / `OnEvent` / `HealthCheck` / `GetCapabilities` देता है (`proto/plugin/v1/plugin_api.proto`)। `metadata.provider` प्लगइन `OnEvent` से संबंधित इवेंट पाता है और `GetCapabilities` से अपनी क्षमता बताता है; यह कोई अलग समृद्धि विधि लागू नहीं करता।

ज़रूरी अनुमति: `api.metadata`।

### `media.read`

प्लगइन मीडिया रिकॉर्ड और स्ट्रीम पढ़ सकता है। मैनिफ़ेस्ट में `media.read` अनुमति से मेल खाता है।

### `media.write`

प्लगइन मीडिया रिकॉर्ड बना या अपडेट कर सकता है। `media.write` अनुमति से मेल खाता है।

### `notification.sender`

प्लगइन सूचनाएँ प्रकाशित कर सकता है। होस्ट बाहर जाने वाले सूचना इवेंट प्लगइन से होकर भेजता है। `notification.sender` अनुमति से मेल खाता है।

### `webhook.receiver`

प्लगइन ख़ुद को वेबहुक एंडपॉइंट के रूप में दर्ज करता है। होस्ट मेल खाते आने वाले HTTP POST अनुरोध gRPC से प्लगइन को भेजता है। क्षमता की घोषणा के अलावा किसी अनुमति की ज़रूरत नहीं।

## अनुमतियाँ

`public` और `prefs` **अनुमतियाँ** हैं, क्षमताएँ नहीं: ये नहीं बदलतीं कि प्लगइन सर्वर की ओर कौन-सी भूमिका निभाता है, ये प्लगइन के iframe को अतिरिक्त पढ़ने/लिखने के दायरे देती हैं। इन्हें मैनिफ़ेस्ट में `permissions` के नीचे घोषित करें।

### `public`

प्लगइन के iframe को सर्वर के गैर-संवेदनशील डेटा तक केवल पढ़ने की पहुँच देता है: `GetPublicMediaItem` / `ListPublicMediaItems`, जो एक **सुरक्षित प्रक्षेपण** लौटाते हैं (id, टाइटल, प्रकार, साल, सारांश, पोस्टर URL), कभी फ़ाइल पाथ, आकार, प्रदाता id या स्ट्रीम नहीं। सर्वर की पहचान (नाम) पहले से सार्वजनिक है और उसे किसी अनुमति की ज़रूरत नहीं। इसे माँगने के लिए `permissions` में `public` घोषित करें।

### `prefs`

प्लगइन के iframe को `PluginUserDataService` (`GetPref` / `SetPref` / `DeletePref` / `ListPrefs`) के ज़रिए प्लगइन के अपने नेमस्पेस में **मौजूदा उपयोगकर्ता** की पसंदें पढ़ने/लिखने देता है। प्लगइन और उपयोगकर्ता iframe टोकन से बँधे होते हैं, इसलिए प्लगइन केवल (अपने-प्लगइन, मौजूदा-उपयोगकर्ता) का डेटा छू सकता है: कभी किसी दूसरे प्लगइन का नहीं, कभी किसी दूसरे उपयोगकर्ता का नहीं, कभी पहचान/सुरक्षा फ़ील्ड नहीं। पंक्तियाँ प्लगइन या उपयोगकर्ता के साथ कैस्केड में हटती हैं। `permissions` में `prefs` घोषित करें।

> **जो आप कभी नहीं माँग सकते।** `admin.*`, `auth.*` (लॉगिन/लॉगआउट/सेशन), `system.*`, और सामान्य `user.write` / `library.write` कड़ाई से बंद हैं: इन्हें किसी भी टोकन से हटा दिया जाता है और API सीमा पर मना कर दिया जाता है, भले ही कोई मैनिफ़ेस्ट इन्हें घोषित करने की कोशिश करे। सर्वर API पर दायरे वाले प्लगइन टोकन को **डिफ़ॉल्ट रूप से मना** किया जाता है: यह केवल उन्हीं विधियों तक पहुँच सकता है जिन्हें ऊपर दी गई अनुमतियाँ स्पष्ट रूप से खोलती हैं।
