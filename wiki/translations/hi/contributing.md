# योगदान

Evey खुले में विकसित होता है, और इसके कोड पर काम करने वालों के लिए लिखे दस्तावेज़
कोड के साथ GitHub पर रहते हैं, इस साइट पर नहीं। यह पृष्ठ उनकी ओर इशारा करता है।

## कहाँ से शुरू करें

| आप चाहते हैं | पढ़ें |
| --- | --- |
| सोर्स से Evey बनाना और चलाना | [DEV.md](../DEV.md) |
| योगदान के नियम जानना: branches, commits, tests, लाइसेंस समझौता | [CONTRIBUTING.md](../CONTRIBUTING.md) |
| आधे घंटे में कोड में अपना रास्ता ढूँढना | [कोड का नक्शा](CODEBASE_MAP.md) |
| परतें और व्यावसायिक संदर्भ समझना | [आर्किटेक्चर](ARCHITECTURE.md) |
| उन परंपराओं का पालन करना जो कोड पहले से मानता है | [कोड परंपराएँ](code-conventions.md) |
| इंटरफ़ेस पर काम करना | [इंटरफ़ेस डिज़ाइन सिस्टम](frontend-design-system.md) |
| जानना कि कोई संरचनात्मक फ़ैसला क्यों लिया गया | [आर्किटेक्चर निर्णय](adr/README.md) |

## निर्णय-अभिलेख क्यों, और कहाँ

हर संरचनात्मक फ़ैसले - हेक्सागोनल बनावट, एक्सटेंशन टोकन का दायरा कैसे तय होता है,
इंस्टॉलेशन एक ही compose फ़ाइल क्यों है, एक ही प्लेबैक योजना सभी क्लाइंट के लिए कैसे
तय करती है - का एक आर्किटेक्चर निर्णय अभिलेख है: संदर्भ, तौले गए विकल्प, क्या चुना
गया और उसकी क़ीमत क्या है। वे रिपॉज़िटरी में, उस कोड के पास रखे जाते हैं जिसे वे
समझाते हैं, और इनमें से किसी फ़ैसले को बदलने का प्रस्ताव देने से पहले शुरुआत इन्हीं
से होती है।

## pull request खोलने से पहले

- `make pre-push` अकेली जाँच-चौकी है। यह CI की नक़ल है: यहाँ हरा चलना मतलब हरी
  pipeline।
- हर नए व्यवहार और हर बग-सुधार के लिए tests अपेक्षित हैं।
- बाहरी योगदान के लिए [योगदानकर्ता लाइसेंस समझौते](../CLA.md) को एक बार स्वीकार
  करना होता है: Evey AGPL-3.0-or-later के तहत है और एक व्यावसायिक लाइसेंस के तहत भी
  दिया जाता है। आपके काम का कॉपीराइट आपके पास रहता है।

सुरक्षा समस्याएँ सार्वजनिक रूप से नहीं बताई जातीं: `security@eveyproject.org` पर
लिखें (देखें [SECURITY.md](../SECURITY.md))।
