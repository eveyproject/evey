# योगदान करें

Evey खुले में विकसित होता है, और इसके कोड पर काम करने वालों के लिए लिखे गए दस्तावेज़ इस साइट पर नहीं, बल्कि GitHub पर कोड के साथ रहते हैं। यह पेज उनकी ओर इशारा करता है।

## कहाँ से शुरू करें

| आप चाहते हैं | पढ़ें |
| --- | --- |
| Evey को सोर्स से बनाना और चलाना | [DEV.md](../DEV.md) |
| योगदान के नियम जानना: ब्रांच, कमिट, परीक्षण, लाइसेंस समझौता | [CONTRIBUTING.md](../CONTRIBUTING.md) |
| आधे घंटे में कोड में अपना रास्ता खोजना | [कोड का नक्शा](CODEBASE_MAP.md) |
| परतों और सीमित संदर्भों को समझना | [आर्किटेक्चर](ARCHITECTURE.md) |
| कोड पहले से जिन परंपराओं का पालन करता है उनका पालन करना | [कोड परंपराएँ](code-conventions.md) |
| इंटरफ़ेस पर काम करना | [फ़्रंटएंड डिज़ाइन सिस्टम](frontend-design-system.md) |
| जानना कि कोई संरचनात्मक चुनाव क्यों किया गया | [आर्किटेक्चर निर्णय](adr/README.md) |
| रिलीज़ बनाना | [रिलीज़ पुस्तिका](runbooks/release.md) |

## निर्णय रिकॉर्ड क्यों, और कहाँ

हर संरचनात्मक चुनाव (हेक्सागोनल लेआउट, प्लगइन टोकन का दायरा कैसे तय होता है, इंस्टॉल एक ही compose फ़ाइल क्यों है, एक प्लेबैक योजना हर क्लाइंट के लिए कैसे तय करती है) का एक आर्किटेक्चर निर्णय रिकॉर्ड है: संदर्भ, तौले गए विकल्प, क्या चुना गया और उसकी क्या क़ीमत है। वे रिपॉज़िटरी में, जिस कोड को वे समझाते हैं उसके बगल में रखे जाते हैं, और उनमें से किसी चुनाव को बदलने का प्रस्ताव देने से पहले यहीं से शुरू करना चाहिए।

## पुल रिक्वेस्ट खोलने से पहले

- `make pre-push` अनिवार्य जाँच (gate) है: यह CI की जाँचें स्थानीय रूप से चलाता है (vet, कमज़ोरी स्कैन, बिल्ड, `-race` के साथ यूनिट टेस्ट, फ़्रंटएंड, lint, आर्किटेक्चर गार्ड)। यह Docker इमेज या Android ऐप नहीं बनाता: `Dockerfile` या Kotlin कोड बदलने के बाद उन्हें ख़ुद बनाएँ।
- नए व्यवहार और हर बग सुधार के लिए परीक्षण अपेक्षित हैं।
- बाहरी योगदान के लिए एक बार [योगदानकर्ता लाइसेंस समझौते](../CLA.md) को स्वीकार करना होता है: Evey AGPL-3.0-or-later है और एक व्यावसायिक लाइसेंस के तहत भी उपलब्ध है। अपने काम का कॉपीराइट आपके पास रहता है।

सुरक्षा समस्याएँ सार्वजनिक रूप से नहीं बताई जातीं: `security@eveyproject.org` पर लिखें (देखें [SECURITY.md](../SECURITY.md))।
