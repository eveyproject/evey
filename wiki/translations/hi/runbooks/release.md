# रिलीज़ रनबुक

Evey का कोई संस्करण एक branch से उस चीज़ तक कैसे पहुँचता है जिसे संचालक पिन कर
सके। पहली टैग की गई रिलीज़ से पहले लिखी गई, ताकि पहली रिलीज़ कोई प्रक्रिया गढ़ने के
बजाय एक प्रक्रिया का पालन करे।

## CI किसी टैग के साथ क्या करता है (टैग करने से पहले पढ़ें)

`.github/workflows/ci.yml` हर push पर और हर `v*.*.*` टैग पर इमेज बनाता और प्रकाशित
करता है, एक्सटेंशन रनटाइम के तीन रूपों में (`` (lean), `-nodejs`, `-full`),
`docker.io/gravityz/evey` और `ghcr.io/evey-project/evey` पर:

| आप push करते हैं | प्रकाशित इमेज टैग (हर एक `-nodejs` / `-full` भी) |
|---|---|
| एक branch (जैसे `beta-0.0.1`) | `beta-0.0.1`, `sha-<short>` |
| टैग `v0.2.0-beta.1` (प्री-रिलीज़: इसमें हाइफ़न है) | `0.2.0-beta.1`, `sha-<short>` |
| टैग `v0.2.0` (स्थिर) | `0.2.0`, `0.2`, `0`, `latest`, `sha-<short>` |

तीन नतीजे:

- **branch टैग खिसकता रहता है।** `beta-0.0.1-full` उसी की ओर इशारा करता है जो सबसे
  बाद में push हुआ; एक दिन के अंतर पर किए गए दो `docker compose pull` अलग-अलग कोड
  चला सकते हैं, और "`beta-0.0.1-full` पर" rollback कहीं नहीं ले जाता। संचालकों को
  `sha-<short>` टैग (या कोई रिलीज़ टैग) पिन करना चाहिए, कभी branch का नाम नहीं - यही
  वह है जो `scripts/evey-update.sh` अंत में छापता है ताकि वे उसे `.env` में डालें।
- **प्री-रिलीज़ कभी `latest` को नहीं छूती।** `latest` का मतलब है सबसे नई स्थिर
  रिलीज़; बंद beta का कोई कट उसे फ़ॉलो करने वाले किसी को नहीं दिखता। (प्री-रिलीज़ को
  `X.Y` / `X` टैग भी नहीं मिलते: वे सिर्फ़ स्थिर रिलीज़ के लिए हैं।)
- **हर build पर Multi-arch** (amd64 + arm64), ताकि ARM संचालक इनमें से कोई भी पिन कर
  सके।

commit बाइनरी में (`evey version`, `/healthz`) और इमेज labels में
(`org.opencontainers.image.revision`) दर्ज होता है, इसलिए "यह कौन सा कोड है?" का
जवाब हमेशा दिया जा सकता है, किसी टैग पर भरोसा किए बिना।

## प्री-रिलीज़ काटना (बंद beta)

1. **ठीक उसी commit पर जाँचें हरी**: स्थानीय रूप से `make pre-push`। push पर CI भी
   यही चलाता है।
2. **पहले किसी असली इंस्टॉलेशन पर साबित।** commit पहले से संदर्भ तैनाती पर
   `sha-<short>` टैग के रूप में चल चुका होना चाहिए, `scripts/evey-update.sh --tag
   sha-<short> --apply` से अपडेट और `--commit <sha>` से जाँचा हुआ। टैग दूसरे संचालकों
   से एक वादा है; उसे सबूत के बाद दें, पहले नहीं।
3. **`CHANGELOG.md`**: `[Unreleased]` की प्रविष्टियाँ तारीख़ के साथ नए संस्करण के नीचे
   ले जाएँ। Keep a Changelog प्रारूप, सिर्फ़ उपयोगकर्ताओं वाली भाषा।
4. **उसी commit से टैग करें**, annotated, और सिर्फ़ टैग push करें:
   ```bash
   git tag -a v0.2.0-beta.1 -m "v0.2.0-beta.1"
   git push origin v0.2.0-beta.1
   ```
5. **CI पर नज़र रखें** जब वह `0.2.0-beta.1` (+ रूप) प्रकाशित करे। फिर संदर्भ तैनाती
   पर `scripts/evey-update.sh --tag 0.2.0-beta.1 --apply` - रिलीज़ टैग पिन करना
   `sha-` वाले पिन की जगह ले लेता है।
6. **टैग की घोषणा करें**, उसके changelog खंड के साथ। संचालक अपनी `image:` पंक्ति में
   `gravityz/evey:0.2.0-beta.1` (या `-full`) पिन करते हैं।

प्री-रिलीज़ टैग सस्ते हैं: ज़रूरत के हिसाब से `-beta.2`, `-beta.3`। पर वे वापस नहीं
लिए जा सकते - प्रकाशित टैग प्रकाशित ही रहता है। किसी ख़राब कट को पलटने के लिए अगला
कट काटें; किसी टैग को कभी दूसरी जगह न मोड़ें।

## स्थिर रिलीज़ काटना

वही चरण, बिना suffix वाला टैग `vX.Y.Z`। एक चीज़ जाँचनी है जिसकी प्री-रिलीज़ को ज़रूरत
नहीं: इमेज में शामिल Postgres का major संस्करण changelog में दर्ज होना चाहिए, क्योंकि
embedded डेटाबेस वाले संचालक को उसके बदलने पर
[installation.md](../installation.md) के upgrade खंड का पालन करना पड़ता है।

## रिलीज़ को वापस लेना

इमेज registry में बनी रहती हैं। संचालक
`scripts/evey-rollback.sh --tag <previous> [--restore <pre-update dump>] --apply` से
वापस जाता है (update script ठीक यही पंक्ति छापता है)। रिलीज़ की तरफ़ कुछ भी पलटना नहीं
पड़ता; सुधार आने पर एक सुधरा हुआ `-beta.N+1` प्रकाशित करें।
