# 转码与服务器容量

转码是[播放决定](how-playback-is-decided.md)中开销最大的结果：直接播放和重封装几乎不消耗服务器资源，也从不占用转码名额。本页说明服务器如何知道自己能编码什么、如何在观众之间分配这份容量，以及满载时会发生什么。

## 服务器会自我测量

容量不是一个需要你估算的设置。服务器会测量它：

- **何时。** 不在启动时：服务器依据之前已知的情况启动（第一次则使用保守的 720p 软件默认值），并在第一个空闲时刻运行测量，即没有人在观看且处理器大多空闲的时候。测量需要几分钟。在负载下进行的测量会被标记为临时，并在机器空闲时重做。
- **测什么。** 对一段 4K 片段进行真实编码，包括 SDR 和 HDR，在处理器以及服务器检测到的每个加速器上进行，形式与真实播放相同。结果是每个设备能实时维持的最高分辨率，以及每种流的开销。
- **再次测量。** 在硬件变化后，或者在 **Admin → 转码 → 编码校准** 中点击 **重新校准** 时。

测量进行期间，需要转码的播放会显示 **服务器正在自我校准**，并被要求稍后重试。直接播放不受影响。

在一台连任何一个分辨率都维持不了的处理器上，服务器仍然提供 720p（SDR）和 480p（HDR），每次一个流。

测量依次使用：你提供的片段、一次性下载并通过 SHA256 校验的参考片段，或者当场生成的合成片段。真实片段的测量比合成片段更准确，合成片段会夸大开销，可能让一台机器被限制得比它应有的能力更低：

```yaml title="docker-compose.yml"
services:
  evey:
    environment:
      EVEY_BENCH_HDR_SAMPLE: /data/bench/my-4k-hdr.hevc
      EVEY_BENCH_SDR_SAMPLE: /data/bench/my-4k-sdr.hevc
```

## 分配容量

**实时播放容量**（**Admin → 转码**）是可以同时编码的视频流数量。它由测量得出，并在硬件变化时自动调整。**限制并发视频流数量** 可以降低它，但永远不能提高它。

- 只重新编码音频（视频直接复制）的转码不占用名额。
- 观众切换画质时仍只占一个名额。
- 只编码观众实际观看的画质，而不是整套画质阶梯。

每个流都交给能服务它的最便宜的路线：一个已证明具备该流所需能力的加速器（例如 HDR 色调映射或 HEVC 输出），或者处理器。处理器和加速器是两个独立的池。当加速器已满时，如果处理器还有空间，新的流可以转到处理器上；当两者都没有空间时，播放器会显示 **服务器正忙于转码其他流**，并可以重试。

有人观看时，服务器自己的后台任务（缩略图、片头检测、媒体分析）会暂停，让播放独占机器：见[后台任务与服务器负载](../operations/background-work.md)。

如果尽管如此，某一类源仍不断让观众等待，服务器会暂时降低它的最高画质，之后再自行解除限制。见[监控与日志](../operations/monitoring.md#how-playback-actually-went)。

## 编码的内容

| | 默认 |
| --- | --- |
| 视频编码 | H.264。当播放器能解码且显卡能编码时用 HEVC；当开启（**AV1 输出**，仅硬件）且播放器能解码时用 AV1。 |
| 分辨率 | 源的分辨率，除非受到限制：播放器的最大值、码率限制，或服务器能实时编码的上限。 |
| 码率 | 跟随源，并按分辨率缩放。**视频码率上限** 会限制它。 |
| 音频 | AAC。见[音频](audio.md)。 |
| 传送方式 | HLS，使用分片 MP4 分段。 |

## 转码缓存

编码后的分段保存在 `evey-cache` 卷的磁盘上，当另一位观众（或同一位观众稍后）以相同的决定播放同一个条目时会被重用。**Admin → 转码缓存** 显示它的大小并可以清空它；**转码缓存预算**（**Admin → 服务器配置 → 服务器设置**）限制它的大小。在一次改变视频编码方式的更新之后清空它，这样就不会有人收到上一个版本的分段。

## 检查实际情况

- **Admin → 正在播放**：每个流、逐条轨道的播放方式，以及编码它的后端。
- **Admin → 转码 → 编码校准**：测得的上限以及正在使用的加速器。
- **Admin → 流媒体质量**：真实观众的播放情况。
- **负载测试**（**Admin → 转码**）：模拟观众以测量服务器能维持多少。只在没有人观看时运行。
